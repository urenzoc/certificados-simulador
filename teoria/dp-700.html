1. Implementar y administrar una solución de análisis

30–35% del examen

Configurar workspaces y capacidad, gestionar el ciclo de vida con Git y deployment pipelines, asegurar y gobernar los datos y orquestar los procesos.

Piezas de Fabric y cuándo usar cada almacén

  • OneLake: un único data lake por tenant (tenant → workspace → elemento). Todas las tablas se guardan en Delta Parquet y los motores (Spark, SQL, KQL, Power BI) leen la misma copia.
  • La capacidad (SKU F2…F2048) se mide en CU. El smoothing reparte los picos; si se agota la tolerancia, primero se rechaza lo interactivo y luego lo de segundo plano. Una capacidad F se pausa desde Azure Portal.
NecesidadAlmacén
Spark escribe; SQL y Power BI solo leen; archivos + tablasLakehouse (con SQL analytics endpoint de solo lectura)
T-SQL de lectura y escritura, transacciones, equipos SQLWarehouse
Streaming, telemetría, logs, consultas KQL de baja latenciaEventhouse (KQL databases)
OLTP con ACID completo y alta concurrencia para una appSQL database en Fabric
Leer datos externos sin copiarlosShortcut de OneLake

Configuración del workspace

  • Spark settings: pool predeterminado, environment predeterminado (runtime + librerías para todos los notebooks nuevos) y high concurrency (varios notebooks comparten una sesión: mismo usuario, mismo lakehouse predeterminado y mismo environment).
  • OneLake: caché de shortcuts (retención 1–28 días). Workspace identity para autenticarse ante orígenes de confianza.
  • Dominios: solo el Fabric admin crea o elimina dominios; el domain admin crea subdominios y asigna workspaces; los domain contributors asignan sus propios workspaces.

Ciclo de vida: Git

  • Azure DevOps: se indica organización, proyecto, repositorio, rama y carpeta. GitHub: URL del repositorio + token (fine-grained con Contents: Read and write).
  • El admin debe habilitar en el tenant la sincronización con Git (y con GitHub, que es un ajuste aparte).
  • En Azure DevOps, para hacer commit el usuario necesita nivel de acceso Basic (Stakeholder no basta) y permiso de contribución.
  • Flujo recomendado: rama de feature → pull request → main, con reglas de protección de rama.

Ciclo de vida: deployment pipelines

  • De 2 a 10 etapas (Dev → Test → Prod), cada una asignada a un workspace.
  • Copian la definición de los elementos: no copian datos, programaciones de actualización ni credenciales, y no ejecutan nada al terminar.
  • Los elementos con el mismo nombre y tipo quedan emparejados y el despliegue los sobrescribe. Los no emparejados se crean como nuevos.
  • Deployment rules cambian conexiones o parámetros en cada etapa.
  • Automatizar con las REST APIs de Fabric desde Azure DevOps o GitHub Actions, autenticando con un service principal.
  • Para validar un warehouse antes de desplegarlo (referencias inválidas): database project.

Gobernanza

  • Endorsement: Promoted (lo hace cualquier editor), Certified (solo revisores autorizados por el admin) y Master data (fuente autorizada de datos centrales). Los dashboards no se pueden respaldar.
  • Sensitivity labels de Microsoft Purview: se heredan aguas abajo y viajan con las exportaciones (Excel, PDF).
  • Lineage view para ver dependencias entre elementos; Purview hub para el catálogo y la auditoría.
  • Conectividad privada: managed private endpoints (Spark/notebooks), on-premises data gateway (pipelines y dataflows). Secretos: notebookutils.credentials.getSecret(url_keyvault, nombre).

Trampas frecuentes

  • Deployment pipeline ≠ data pipeline: la primera mueve definiciones entre workspaces, la segunda mueve datos.
  • Las programaciones de refresh y los datos del lakehouse no viajan en un despliegue.
  • Para leer solo por SQL no se da un rol de workspace (vería todo): se comparte el elemento con Read all SQL endpoint data.
  • Viewer no puede ejecutar notebooks; Contributor es el mínimo para ejecutarlos y escribir.
  • El retry se configura en cada actividad, no en el pipeline completo.

2. Ingerir y transformar datos

30–35% del examen

Elegir el método de carga, transformar con PySpark, SQL o Power Query, procesar streaming y diseñar cargas completas e incrementales sobre un modelo dimensional.

Cargar archivos de Azure Storage en un warehouse con T-SQLCOPY INTO
  • Staging se activa al cargar un Warehouse desde orígenes on-premises u otros que no son ADLS/Blob (p. ej. Snowflake).
  • Fast copy en Dataflow Gen2 para volúmenes grandes; incremental refresh con una columna fecha/hora y destinos Lakehouse, Warehouse o Azure SQL.
  • Caché de shortcuts: solo GCS, S3, S3 compatible y gateway (no ADLS Gen2), archivos ≤ 1 GB, retención 1–28 días que se renueva con cada lectura. Minimizar egress sin copiar datos = shortcut + caché.
  • Para que un Eventstream capture inserts/updates/deletes de Azure SQL hay que habilitar CDC en la base y en la tabla.

Power Query (M) en Dataflow Gen2

  • Estructura let … in. Funciones típicas: Table.FirstN, Table.TransformColumnTypes, Table.RenameColumns(t, {{"ProductKey","ProductID"}}).
  • Merge queries = join entre consultas (Left outer conserva toda la izquierda). Append queries = apilar filas.

Eventhouse y KQL

Visits
| where orderedAmount > 150 and VisitTime > ago(24h)
| extend Dia = startofday(VisitTime)
| summarize Total = sum(orderedAmount) by userID, bin(VisitTime, 1h)
| order by Total asc          // order/sort by es descendente por defecto

StockTrades

| extend Cambio = ClosePrice - Prev
  • project elige columnas; extend agrega columnas; take limita filas; distinct deduplica; union apila; iff()/case() condicionales; row_cumsum() suma acumulada; row_window_session() sesiones.
  • Por defecto join es innerunique. Rendimiento: filtrar lo antes posible y poner la tabla más pequeña a la izquierda.
  • Update policy: se define en la tabla destino; su función lee lo que se ingiere en la tabla origen y escribe el resultado transformado.
  • OneLake availability: expone las tablas como Delta; solo replica datos nuevos salvo que se elija aplicar a las tablas existentes, con una latencia de hasta unas horas configurable.

  • Dimensión = atributos descriptivos (ID, nombre, color…); hecho = medidas y claves (montos, cantidades, fechas de transacción).
  • Desnormalizar categorías y subcategorías dentro de DimProduct; usar claves sustitutas enteras.
  • Carga incremental con watermark (Lookup del último valor + Copy filtrado + actualizar el watermark) o con MERGE (upsert).

  • Medallion: bronze (datos tal cual), silver (limpios, tipados, sin duplicados), gold (modelo dimensional).
from delta.tables import DeltaTable
if not spark.catalog.tableExists("dim_producto"):
    df.write.format("delta").mode("overwrite").saveAsTable("dim_producto")
else:
    (DeltaTable.forName(spark, "dim_producto").alias("t")
       .merge(df.alias("s"), "t.ProductID = s.ProductID")
       .whenMatchedUpdateAll(condition="t.hash <> s.hash")
       .whenNotMatchedInsertAll()
       .execute())

Trampas frecuentes

  • Shortcut no copia datos; Copy y Dataflow sí.
  • ADLS Gen2 no usa la caché de shortcuts (ya está en Azure).
  • Aggregate ≠ Group by: la ventana de tiempo está en Group by.
  • order by en KQL es descendente por defecto; en SQL es ascendente.
  • Dataflow Gen1 es la versión heredada de Power BI y no escribe en destinos de Fabric: elige Dataflow Gen2 o un pipeline.

Alertas

  • Activator: vigila datos (Eventstream, KQL, informes de Power BI) y dispara emails, Teams o flujos cuando se cumple una condición.
  • En pipelines: actividad de notificación con dependencia On fail.

Mantenimiento de tablas Delta

ComandoEfecto
OPTIMIZE tablaCompacta muchos archivos Parquet pequeños en pocos grandes
OPTIMIZE tabla ZORDER BY (col)Además agrupa los datos por columnas de filtro
OPTIMIZE tabla VORDERReescribe aplicando V-Order
VACUUM tabla RETAIN 168 HOURSBorra archivos ya no referenciados por el log (por defecto 7 días)
  • También se ejecutan desde el lakehouse: … junto a la tabla → Maintenance (marcar OPTIMIZE/V-Order/VACUUM → Run now).
  • V-Order acelera la lectura (Direct Lake, SQL, Power BI) a cambio de una escritura algo más lenta: deshabilitarlo en warehouses de escritura intensiva o tablas de staging que se leen una vez.
  • Optimize Write reduce archivos pequeños al escribir. Particionar por columnas de filtro de baja cardinalidad (fecha, región).

Optimizar Spark, warehouse y Power BI

  • Spark: high concurrency para compartir sesiones, environments con librerías ya instaladas (evita instalarlas en cada notebook), autoscale, broadcast joins, caché.
  • Warehouse: claves sustitutas enteras (no hash MD5/strings), estadísticas al día, tipos de datos ajustados.
  • Direct Lake: V-Order, tablas compactadas; RLS definida en el SQL endpoint o vistas puede forzar fallback a DirectQuery y ralentizar.
  • Eventstream: ajustar el Event throughput. Dataflow Gen2: staging y fast copy. Copy: degree of copy parallelism.

Memoriza

  • Monitoring hub = vista central; Runtime logs = causa del error del Eventstream; Data insights = cuántos errores.
  • OPTIMIZE compacta, VACUUM limpia, V-Order acelera la lectura y ralentiza la escritura.
  • Semantic link para refrescar y seguir un modelo desde código.
  • queryinsights para historial; sys.dm_exec_requests para lo que corre ahora.

Trampas frecuentes

  • VACUUM no compacta; OPTIMIZE no borra archivos antiguos.
  • Aumentar la capacidad casi nunca es la respuesta cuando piden minimizar costos.
  • La columna Capacity del Monitoring hub no es el workspace: es Location.
