1. Diseño de aplicaciones

Traducir requisitos de negocio en prompts, tareas de modelo, cadenas y agentes.

  • Prompts con formato de salida explícito (JSON con campos, lista, longitud); delimitadores; ejemplos few-shot; instrucciones de qué hacer si no hay información.
  • Elegir la tarea del modelo: clasificación, extracción, resumen, traducción, generación, embeddings, reranking.
  • Cadena = componentes con entradas y salidas encadenadas (recuperador → prompt → LLM → parser).
  • Agentes: definir y ordenar herramientas para razonamiento en varios pasos (p. ej. buscar → calcular → responder).

2. Preparación de datos

Chunking, extracción, almacenamiento en Delta y evaluación de recuperación.

Estrategia de chunkingCuándo
Tamaño fijo con superposiciónTexto homogéneo; simple
Por estructura (secciones, títulos, párrafos)Documentos con jerarquía (manuales, contratos)
SemánticoCortar donde cambia el tema
Jerárquico / padre-hijoRecuperar fragmentos pequeños y devolver el contexto mayor
Añadir título/sección al chunkEvitar que el fragmento pierda su contexto
  • El tamaño del chunk debe caber en el contexto del modelo de embeddings; chunks pequeños = más precisión, grandes = más contexto.
  • Filtrar contenido extraño (encabezados, pies de página, menús, avisos legales repetidos) que degrada la recuperación.
  • Extracción: pypdf/PyMuPDF (PDF), unstructured (varios formatos), python-docx, BeautifulSoup (HTML); ai_parse_document en Databricks.
  • Flujo: leer archivos de un volumen → extraer → chunk → escribir en una tabla Delta de UC (con id y metadatos) → habilitar Change Data Feed → índice de Vector Search sincronizado.
  • Reranking: un segundo modelo reordena los candidatos recuperados por relevancia real; mejora precisión.

3. Desarrollo de aplicaciones

Frameworks, prompts, guardrails, selección de modelos y agentes con MLflow.

  • Frameworks: LangChain / LangGraph, LlamaIndex, DSPy; Mosaic AI Agent Framework + MLflow para registrar y desplegar.
  • Aumentar el prompt con contexto recuperado y datos del usuario (RAG).
  • Mover la salida del LLM: instrucciones más específicas, ejemplos, rol, restricciones, formato.

Guardrails

  • De entrada: detectar jailbreak/inyección, temas prohibidos, PII. De salida: toxicidad, alucinaciones, políticas. Modelos tipo Llama Guard; AI Gateway con filtros de seguridad y PII.
  • El guardrail que bloquea devuelve error (p. ej. 400) y queda registrado.

4. Ensamblaje y despliegue

pyfunc, Unity Catalog, Model Serving, Vector Search, ai_query y CI/CD.

  • pyfunc personalizado: clase con load_context y predict para incluir pre y postprocesamiento.
  • Registrar con MLflow en Unity Catalog (mlflow.set_registry_uri("databricks-uc"), nombre cat.esq.modelo), con firma, ejemplo de entrada y dependencias; alias como @champion.
  • Model Serving: autenticación del endpoint a recursos (Vector Search, tablas) con service principal / passthrough automático; nunca credenciales personales.
  • Foundation Model APIs: pago por token (modelos alojados por Databricks) o rendimiento aprovisionado (producción, latencia garantizada); también modelos externos vía AI Gateway.
  • ai_query() para inferencia por lotes desde SQL sobre tablas.

Trampas frecuentes

  • Storage-optimized no significa más rápido: significa escala y costo.
  • Triggered es más barato que Continuous.

5. Gobernanza

Enmascarar, proteger entradas y respetar licencias.

  • Enmascarar PII como guardrail (antes de indexar y en la salida).
  • Guardrails contra entradas maliciosas: detección de inyección y jailbreak, listas de temas permitidos.
  • Revisar licencias y términos de las fuentes de datos y los modelos (uso comercial, atribución).
  • Texto problemático en las fuentes: filtrar, moderar o reemplazar antes de incorporarlo; restringir a fuentes confiables.

6. Evaluación y monitoreo

MLflow evaluate, jueces, inference tables, AI Gateway y costos.

  • mlflow.genai.evaluate() con scorers integrados y personalizados; tracing de MLflow para ver cada paso del agente.
  • Jueces que requieren referencia (ground truth): Correctness, RetrievalSufficiency (expected facts). No la necesitan: RelevanceToQuery, RetrievalGroundedness, Safety, Guidelines.
  • Inference tables registran solicitudes y respuestas del endpoint para analizar RAG en producción; Agent Monitoring evalúa tráfico en vivo.
  • AI Gateway: límites de tasa (QPM = consultas por minuto), seguimiento de uso en system.ai_gateway.usage, guardrails, fallbacks.
  • Controlar costos: modelo más pequeño, menos tokens de contexto, caché, batch con ai_query, límites de tasa.
  • Incorporar feedback de expertos (SME) con la Review App y etiquetado para mejorar el agente.
